## 2026-11-09～10｜架構規劃的演變

1. **導演版**：故事、世界、鏡頭三層；8 階段 3 關卡；主角物件、分層生圖、張力曲線。
2. **對齊使用者流程**：使用者說喜歡「grill me → 三種風格樣張 → 完整生成」。改成使用者只參與三個時刻，其餘在幕後自動完成；加入 brief 檔解決「直接接續對話」的資訊流失。
3. **情境適配**：使用者問是否適用各種簡報類型（科普、分享、提案、成果、成長、開場、會議、洽談），而且這些都常做。加入 5 個維度、快速／標準／旗艦模式、依章節調整的旋鈕、可儲存的世界。
4. **自評優缺點後修正**：
   - 太複雜 → 精簡，規則交給腳本
   - 技術風險 → 先實驗、三級退路、單一 HTML 核心
   - 依賴 AI 品味 → 獨立評審、內容與引擎分離、PPTX 文字可編輯
5. **使用者質問「憑什麼讓人買單」**：
   - 結論：架構和點子都能被抄，真正的差異是越用越省事、一個 Skill 打天下、處理交付後的需求。
   - 證據比架構重要：8 種情境的成品、前後對比、時間曲線。
6. **使用者分享心法**（見 `inputs/presentation-principles.md`），兩次修正 Claude：
   - 標題只說這頁在講什麼，重點放在內容裡，不寫結論句。
   - 不寫承接、引出的過場文字，位置感靠目錄點亮和頁籤。
7. **震撼頁**：使用者說明獨立重點頁只給情緒轉折或刻意震撼（One more thing）。重點分兩級：一般重點、震撼頁。
8. **架構即目錄**：
   - 使用者指出列舉框架沒抓到核心邏輯。
   - 歸納出「起點 → 終點、一條軸、單一方向」模型。
   - 用 5 個情境題驗證並列型：使用者為了不得罪人選流程排序，並列不會出現在最上層，排序依會議性質而定。
   - 補上「價值軸／中性軸」與兩個層次。
9. 整合成定案規劃：`outputs/architecture-plan.md`

## 2026-11-14｜更正：一頁式不等於快速模式；第四次迭代的測試範圍

- Claude 在說明「第四次要什麼樣的會議簡報」時寫錯了：說前三次「都有情緒或衝擊的設計」「都是完整流程」。使用者指出第三次（年度成果）沒有震撼頁、而且當時規定只能一頁。
- 澄清：
  - **一頁式（`format: section`）是版面限制**
  - **快速模式是製作流程**（Grill 精簡、沿用風格、跳過樣張）
  - 第三次屬於前者，不屬於後者
- 修正後的測試盤點：
  - 已測過：沒有震撼頁與高密度、版面限制（只能一頁）、抽象層次由上往下
  - 未測：當場拍板、結論先行（重要性軸）、會議中被打斷與跳頁、快速模式
  - 第四次（會議簡報）聚焦前三項；快速模式等下一份趕時間的真實簡報再驗證

## 2026-11-14｜改寫 git 歷史，移除外洩的真實資料

- 使用者決定：改寫歷史並強制推送。
- 範圍：只改 `presentation-skill-generation` 分支，`main` 不動。
  - 含真實資料的 commit 有 4 個，從 v0.3 到第四次迭代的比對結論。
  - 涉及的檔案：年度成果範例（storyboard 與 deck.html）、LOG 裡的一行、lint.py 的一段註解，以及包著同一段註解的 `.skill` 壓縮檔。
- 做法：用 `git filter-branch --tree-filter`，在每個受影響的 commit 裡換成現在的虛構內容；lint.py 有變動的 commit 就重新打包 `.skill`。
- 驗證：
  - 所有 commit 的文字檔沒有命中
  - 所有 `.skill` 壓縮檔內部沒有命中
  - 改寫後的最終檔案與改寫前完全相同
- 用 `--force-with-lease` 推送，只有遠端仍是上次推的版本時才覆蓋。
- 副作用：
  - filter-branch 不保留 commit 的 SSH 簽章，所以分支上**所有 commit 的編號都變了**，包括內容沒變的前 8 個。其他地方若有舊的副本，要重新抓取。
  - GitHub 可能仍保留舊 commit 的快取，用舊編號直接存取還看得到，直到 GitHub 清理為止。要立即清除，需要聯絡 GitHub Support。
