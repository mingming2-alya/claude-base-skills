# 定期進度回報

> 什麼時候讀：使用者要做週會、月會的進度回報、專案群總覽，或要整理多個單位交上來的回報時。

進度回報和其他簡報不同：
- **結構通常已經固定**，因為有模板，主管也習慣了。
- **內容由很多人填寫**。
- **每期都要重做**。

所以重點不是設計新架構，而是三件事：**讀懂模板、提高內容品質、讓總覽一眼看出問題**。

## 1. 先拿到模板（輸入物）

模板、空白表單、前一期的回報都是**輸入物**，在提出任何改法之前就要拿到並讀完。如果模板只存在於成品裡，請使用者另外提供一份空白模板或前一期的回報。

為什麼：真實案例裡，Claude 沒看到模板就建議「風險寫成問題 → 影響 → 誰、何時解決」，結果模板早就有這五欄。真正的問題是**大家沒有填**，不是欄位設計。

讀模板時要確認：
- 每一區的欄位是什麼，順序能不能改。重排通常需要主管同意，先問。
- 模板裡有哪些欄位常常被留空？那通常才是真正的問題。

## 2. 單位回報的填寫規範（可以直接發給各單位）

模板不動，只要求寫法：

**里程碑**
- 標出每個里程碑的狀態：已完成、進行中、目標日期。
- 落後時寫「落後 N 天」，並註明能不能追回。

**本週完成**
- 每條寫成「**做到什麼＋數字**」：完成幾項、比例多少、處理幾筆、正確率多少、比計畫快或慢幾天。
- 最多 3 條，最重要的放第一條。
- 不要只寫活動，例如「啟動資料收集」「盤點痛點」，要寫結果，例如「收集 6 個部門、共 42 份報告」。
- 小標題底下的子項目有數字也可以，例如「RAG 維護：P1 370 筆完成」。

**下週工作**
- 每條寫成**可以驗收的目標**：做到什麼，加上數字或完成日期（ETA）。

**重要問題**
- 照模板的欄位填：問題 → 影響 → 解決方案 → 完成日期 → 負責人。
- 沒有風險時，寫一行「**本週無風險**」，不要留「/」。主管才知道這是確認過的，不是忘了填。

**沒有進度時**
- 寫「本週無更新」並附原因，例如等待資安審核、等待採購。**不要留白頁**。

## 3. 內容檢查（多人填寫的品質關卡）

各單位交上來後、開會前，跑：

```bash
python3 <skill>/scripts/check_reports.py weekly.pptx --out check-report.md
```

它會逐頁找出三種問題：
- 本週或下週一半以上的項目沒有數字、也沒有明確結果
- 欄位空白
- 問題表全空

輸出的報告可以直接轉給各單位修改。欄位名稱不同時，用 `--this-week`、`--next-week`、`--risk-header` 指定。需要 python-pptx：`pip install python-pptx`。

這是啟發式檢查，會有誤判。例如「等待簽單」雖然沒有數字，但已經是明確狀態。請把報告當成**提醒清單**，不要當成判決。

## 4. 總覽（彙整所有單位）

用 `layout: status-table`。規則：

- **頂端放本期摘要（`summary`）**：依大類各一行，每行要有**數字或明確狀態**。某案本週沒有更新，也要寫出來。這是總覽的「結論先行」。
- **依大類分組（`groups`）**，大類的順序每期固定，主管才找得到位置。
- **所有案例共用同一組階段（`stages`）**，例如啟動 → 需求 → 建置 → 適配。共用階段才能互相比較。
- **每列都要有風險燈號（`risk`: red／yellow／green）**；紅燈與黃燈要寫**需要的支援（`support`）**或原因（`note`）。只有進度百分比，主管三秒內看不出哪裡有問題。
- **同一類之內先排風險高的，同風險再依進度排**（lint 會檢查）。如果某一類要依其他方式排序，設 `order: progress` 並在 `note` 說明，例如「依進度排列」。
- 一頁最多 13 列。案例太多就拆成兩頁，第二頁設 `continued: true`、不放摘要。

範例：`outputs/examples/progress-overview/storyboard.yaml`（內容為虛構示意）。

## 5. 定期重做

- 每期沿用同一份 storyboard 與主題，只更新數字與狀態。
- 適合用快速模式：不需要 Grill 架構，也不需要三選一樣張。
