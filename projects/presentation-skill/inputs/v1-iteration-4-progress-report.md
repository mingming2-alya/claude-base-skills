# v1 第四次迭代：定期進度回報（2026-11-14）

> 依使用者決定「只記抽象結論」：不含公司、單位、專案名稱與實際數據。

## 測試方式

- 案例：一個 AI 推動專案群的週進度會議，**兩份產出**：
  1. 各單位的週進度回報：固定模板，每單位約 3 分鐘，主要時間在主管問答
  2. 使用者用 AI 彙整的「兩頁總覽」：案例太多，所以兩頁
- 聽眾：副總、推動組主管與處長、業務單位主管、推動窗口。
- 主管當時的回饋：部分單位寫得**太流水帳、該有數字的沒有具體數字**。
- 用互動表單 Grill，取得共識後才打開兩份成品（盲測）。

## Grill 得到的共識 brief

- 終點：三秒看出有沒有問題、時程有沒有守住、哪裡需要支援。誠實揭露風險，不放震撼頁。
- 單位回報（使用者選擇**模板不動、只改寫法**，因為重排需要主管同意）：
  - 里程碑要標完成、進行中、落後天數。
  - 本週與下週各一句結論，加最多 3 條，每條都帶數字（完成度、產出、效益）。
  - 風險寫「問題 → 影響 → 誰、何時解決」。
- 兩頁總覽：依專案大類固定排序；每類之內先排風險程度，再排推動進度；每個案例要有燈號、里程碑、關鍵數字。

## 成品（抽象化）

**單位週回報（14 頁）**：每頁的模板是「里程碑時間軸 → 本週完成／下週工作（兩欄）→ 重要問題表（問題、影響、解決方案、完成日期、負責人，附風險色標）」。
- 有些單位寫得具體，例如案例數、工作流數量、完成比例。有些只列活動，例如「啟動資料收集」「盤點痛點」，沒有結果也沒有數字。
- **大多數單位的問題表是空的**（只填「/」），只有一個單位真的寫了風險。
- 有 2 頁整頁空白，連「本週無更新」都沒寫。

**兩頁總覽**：
- 頂端「本次進度更新 Summary」：依案例大類各一行，**帶關鍵數字**（正確率、轉譯比例、可聯網設備數），也寫了「某案本週無更新」。
- 表格：依大類分組；所有案例共用同一組**生命週期階段欄**（啟動 → 需求 → 建置 → 適配），每格標已完成、進行中加日期、目標加日期；最右邊是進度百分比。
- 第二頁的一類寫明「依進度排列」。**整份總覽沒有風險或燈號欄，也沒有「需要支援」**。

## 比對結果

### 對的地方

1. **模板理解正確**：里程碑、本週與下週、問題表的順序與 brief 一致。
2. **「流水帳」的診斷正確**：問題出在寫法，不在模板結構。成品裡同一個模板，有的單位寫出數字、有的沒有。
3. **總覽依大類固定排序**：一致。

### brief 比成品多想到的（成品的改善空間）

1. **總覽沒有風險燈號、也沒有需要的支援**。使用者在 Grill 說終點包含「哪裡需要支援」、要「誠實揭露風險」，但成品只顯示進度。主管三秒內看不出哪裡有問題。
2. **單位問題表幾乎全空**：誠實揭露風險的目標沒有達成。

### deck-architect 漏掉的（v1 要修的）

1. **沒讀到模板就提改法**：brief 建議風險寫成「問題 → 影響 → 誰、何時解決」，其實模板早就有這五欄。原因是模板只存在於成品裡，盲測時 Claude 沒看到。
   → 流程：模板、空白表單、前一期的回報算是**輸入物**，Grill 要請使用者另外提供。如果它只存在於成品裡，就請使用者截一張空白模板。
2. **總覽頂端的摘要**：成品依大類各寫一行重點並附數字，這正是結論先行；brief 的總覽沒有這一層。
   → 規則：總覽頁頂端放「本期摘要」，依大類各一行，每行要有數字或明確狀態。沒有更新也要寫出來。
3. **缺少「狀態表」版型**：進度回報的核心是一張分組表格，包含共用的階段欄、狀態點、日期與進度條。deck-architect 目前的版型都不適合。
   → 新增版型 `status-table`：分組列、共用階段欄、每格狀態（完成／進行中／目標＋日期）、進度百分比，以及**風險燈號與需要的支援**（補上成品缺少的部分）。
4. **多人填寫的品質關卡**：週回報是各單位各寫一頁，品質不一。deck-architect 只檢查自己產出的簡報。
   → 新增「填寫規範」與內容 lint，給各單位用：本週與下週每條要有數字或明確產出；問題表全空時提問「真的沒有風險嗎？」；整頁空白要改寫成「本週無更新＋原因」。

## v1 四次迭代總結

| | 第一次 | 第二次 | 第三次 | 第四次 |
|---|---|---|---|---|
| 類型 | 主管期許演講 | 工具推廣說明 | 年度成果（非盲測） | 定期進度回報 |
| 聽眾、終點、顧慮 | ✓ | ✓ | ✓ | ✓ |
| 架構 | 漏既有框架 | 既有框架問太晚 | 驗證「最上層不可並列」 | 模板理解正確，但沒讀到模板 |
| 新缺口 | 故事位置、語氣、時間 | 證據、限制、查核、頁數 | 計畫轉成果、一頁總覽、附件 | 總覽摘要、狀態表、多人填寫關卡 |

結論：
- **情境判斷四次都正確**。
- **架構推導**在先問、先讀既有框架之後就穩定了。
- 缺口從「架構」逐步轉向「**內容品質**（證據、數字、誠實）」與「**特定類型需要的版型**」。

這表示核心模型已經站穩，下一步的價值在版型與品質關卡。
