## 一、他的做法（十個機制）

### 1. 設計樹＋前沿，一輪問完所有互不依賴的題目（`grilling`）
把要決定的事畫成樹：每個決定下面掛著依賴它的決定。每一輪只問「前置條件都已確定」的題目，而且一次問完；題目編號，每題附推薦答案，措辭讓回答「是」就等於接受推薦。答完重新計算下一輪。設計說明裡的數字：13 題通常 3 輪問完。
→ 我們已採用（v4.4 起）。

### 2. 查事實是 Agent 的事，做決定是使用者的事（`grilling`）
能從環境查到的事實，派全新上下文的子代理去查，不問使用者；查的同時，不依賴它的題目照常問。Agent 自己回答決定題，等於壞了這個技能。
→ 我們已採用（Pre-Flight）。

### 3. 用使用者自己的話回答，不用選單（`.out-of-scope/native-question-tool.md`）
他明確不讓訪談走 `AskUserQuestion` 這類選單工具。理由是選單會把 Agent 推向「預先寫好答案的多選題」，而訪談要的是**用自己的話回答的開放題**、一次走一條分支。想用選單的人可以在自己的 `CLAUDE.md` 寫一行偏好。
→ **與我們最大的差異**：本專案規則三要求所有問題都用互動表單。表單本身不是問題，問題在選項替使用者先寫好了答案。

### 4. 先發散、後收斂：從第一句話就收素材碎片（`writing-fragments` → `writing-beats`／`writing-shape`）
發散階段不碰結構，只把對話中冒出來的東西（一句好句子、一個場景、半成形的想法、原話、抱怨、笑點）逐條追加進一份碎片檔，**從使用者的第一句話開始收**。最有價值的碎片是「承重母題詞」。收斂階段才把碎片當原料挖，決定結構。
→ 我們只取了承重母題，並用「1–3 顆故事種子」代替碎片檔；使用者在對話中說過的原話與想法沒有被系統性收下來。

### 5. 從開場長出結構，一步一步共同建（`writing-shape`、`writing-beats`）
先寫 2–3 個候選開場，每個開場隱含不同的主張；要使用者選一個或混搭。之後每一步問「有了這個開場，聽眾接下來需要聽到什麼？」，只能用已著陸的概念；每一步都追問：
- 這一段做了上一段沒做的什麼？
- 拿掉它，哪裡會斷？
- 這段在做兩件事，要拆開還是只留一件？
- 開場承諾了 X，現在跑到 Y：要拉回來，還是改開場？
→ 我們給三個完整候選讓使用者挑或混搭；「拿掉會斷什麼」「開場承諾有沒有兌現」這類結構追問沒有寫進流程。

### 6. 失敗模式是「被動同意」（`docs/productivity/grill-me.md`）
最常見的失敗是使用者一路回答「同意、同意、同意」，最後拿到一份 Agent 寫、自己只是點頭的計畫，因為很長所以感覺很踏實。判斷訪談有效的訊號：使用者至少反對過一次；最後落在自己沒預料到的地方；結束時能向不在場的人說明每個選擇。「我不知道」是有效答案。
→ 我們的關卡都是「推薦放第一個」，加上 v4.8.2 的「重提案、輕審問」，被動同意的風險更高；流程裡沒有任何防範。

### 7. 講不清楚的題目，做個粗略的東西來看（`grill-me.md`「可訪談與不可訪談」、`prototype`）
「這樣的感覺對不對」這類題目，靠討論很難定，越聊越長；應該停下來做一個便宜、粗略的東西（大綱、草稿、雛形）讓使用者反應，再回來一句話定案。
→ 對簡報而言，架構的雛形就是「只有每頁題目的空殼清單」或「一分鐘口述稿」。我們的 30 秒口述邏輯鏈是一種，但逐頁層級沒有。

### 8. 答案在別人腦中時，做一份問卷給那個人（`to-questionnaire`）
使用者答不出來的題目（例如需要主管或客戶決定），不要硬問；只問使用者兩件一定答得出的事：要寄給誰、需要對方回答什麼，然後產生一份給那個人填的問卷，答案回來再繼續訪談。
→ 對應我們的缺口 2：幫主管做簡報時，主管想強調什麼、不能講什麼，應該是一份給主管的短問卷，而不是讓使用者猜。

### 9. 迷霧與範圍外分開記（`wayfinder`）
「還看不清、但在範圍內」的事記在「尚未確定」，隨進度轉成明確的題目；「刻意不做」的記在「範圍外」，不會回來。兩者不混。目標（destination）最先確定，因為它決定範圍。
→ 我們有排除清單（範圍外），沒有「尚未確定與假設」清單；還沒定的事容易被當成已定。

### 10. 改了很貴的決定要留下理由（`domain-modeling` 的 ADR 條件）
同時符合三個條件才記決策紀錄：難以反悔、沒有上下文會讓人困惑、真的在幾個選項中取捨過。對話過程是第一手資料，摘要會流失「為什麼」（`ask-matt/PHASE-BOUNDARIES.md`）。
→ 對應我們的缺口 5：在 1a 標出改了最貴的決定並寫下理由，後面的步驟才知道哪些不能隨便動。

另外兩點值得注意：
- 他的訪談一輪可以有十幾題；我們的表單工具一次最多 4 題，一輪要拆好幾張，感覺更長。可以借「回答是就接受推薦」的寫法：把低風險的預設建議合成一題「這幾項照推薦？」，獨立題只留給高風險或要使用者自己寫的題目。
- 他不設題數上限；訪談太長代表範圍太大，應該拆開。我們 v4.8.2 寫了「絕不連問 25 題」，兩者精神一致：重點是不問低價值的題目，而不是設上限。

## 三、建議怎麼融進 Step 1（對應七項缺口）

1. **深挖題的表單寫法**（機制 3）：開放題的選項只給「怎麼進行」（例：我在「其他」寫下來／先跳過，等看到候選再說／請先給我幾個切角），不給現成答案；收斂題照舊推薦放第一個並附理由。
2. **素材碎片簿**（機制 4，強化缺口 1）：從使用者第一句話開始，把原話、案例、半成形想法逐條收進 `brief.md` 的「素材碎片」（或獨立 `fragments.md`）；Round 0 先問「你心裡現在想怎麼講」；三個候選要標明用到哪些碎片；故事種子改成使用者在碎片中標的重點。
3. **硬限制與問卷**（機制 8，缺口 2）：1a 問誰上台、誰能否決結構、指定章節或模板、議程位置、會後是否寄出；使用者答不出來、要主管決定的，產生一份 3–5 題的短問卷給主管，答案回來再繼續。
4. **候選比較＋結構追問＋尚未確定清單**（機制 5、9，缺口 3）：關卡 1a 前用同一組標準比三個候選（主受眾的第一個問題在第幾章被回答、證據就緒度、時間頁數、前提假設、用到的碎片）；選定後逐章做「拿掉會斷什麼」「開場承諾有沒有兌現」檢查；列出「尚未確定與假設」，各自寫怎麼定（查資料／問主管／做雛形）。
5. **雛形試看**（機制 7，缺口 4）：拿不定主意的兩個候選，各做一份「只有每頁題目的空殼清單」對照；Step 2 之後的新關卡，用同一種空殼清單（每頁題目＋內容形狀＋視覺主角）讓使用者確認。
6. **防被動同意**（機制 6，新增）：關卡附上推薦方案最弱的一點與最沒把握的假設，請使用者判斷；整輪都接受推薦時，再追問一題「最沒把握的是哪一個」。
7. **貴的決定留理由**（機制 10，缺口 5）：1a 標出四個改了最貴的決定（理性終點、主受眾、軸與敘事主幹、範圍），寫下理由；另寫「架構變更回路」說明哪些改動便宜、哪些要回 1a。
