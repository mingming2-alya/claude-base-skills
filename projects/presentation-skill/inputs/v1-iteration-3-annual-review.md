# v1 第三次迭代：年度成果報告（2026-11-14，非盲測）

> 依使用者決定「只記抽象結論」：不含公司名稱、專案名稱與實際數據。
> **非盲測**：使用者先提供了最終採用的版面，所以這次不是「Grill 後比對」，而是用 deck-architect 的模型**反向拆解**：檢查模型能不能解釋為什麼採用版比較好。

## 情境

- 一個部門的年度成果，作為總處年終報告的**其中一個章節**，向副總現場報告；這次沒有可點入的附件。
- 原本是課長請使用者把「年初工作重點報告」改成年末版。使用者說這是自己的**架構盲區**：明明照著年初的形式（三個區塊、細節點入附件），年末的架構卻變了，而且比較乾淨。

## 年初版 vs 年末採用版

| | 年初工作重點 | 年末採用版 |
|---|---|---|
| 主標 | 三行總結 | 一句平行的口號（三個動詞） |
| 區塊 | 基礎運維 → 客製 → 創新 | 戰略 → 價值落地 → 基座 |
| 最上層結構 | **並列**（工作類型） | **路徑**（抽象層次由上往下） |
| 用語 | 工作／活動語言 | 成果語言（「創新」改成「價值」） |
| 刪減 | 無 | 整塊刪掉「客製」 |
| 數字 | 在附件裡 | 放上主頁：效益金額、需求件數、完成與推動中的件數 |
| 版面 | 三塊 | 三欄由左上往右下逐階降低，基座在最下面 |

## 模型能解釋的部分（驗證了既有規則）

1. **最上層不能是並列**：年初版是三種工作類型並列，沒有方向；年末版改成「方向 → 價值 → 支撐」的路徑。這是第一次有真實案例同時呈現「錯的版本」和「對的版本」，直接驗證了 `structure.md` 的兩個層次規則。
2. **起點決定方向**：聽眾是副總，最在意總處在 AI 上往哪走，所以戰略放第一。
3. **停靠點命名平行**：三個英文字首與三個中文動詞一一對應。
4. **證據放主頁**：呼應第二次迭代補上的證據規則。
5. **版面編碼軸向**：三欄的高低就是邏輯的上下，對應「視覺由軸推導」的設計。

## 模型解釋不了的部分（新缺口）

1. **既有框架本身是並列的**：v0.1 規定既有框架一定要列為候選，但沒有規定「它若是並列，要提醒並提出路徑版本」。
2. **計畫轉成果**：年度成果報告常常從前一份計畫改寫。Grill 沒問「有沒有前一版」，也不會提醒三件事：用成果語言、依聽眾重排順序、刪掉沒有成果或不屬於這條路徑的區塊。
3. **一頁總覽、作為大簡報的一章**：deck-architect 只會產生有封面的完整多頁簡報，沒有「單頁章節」模式，也沒有「三欄支柱＋關鍵數字」的版型。
4. **可點入的附件**：使用者說有些簡報需要（年初版就有）。HTML 可以做到：總覽區塊點進細節頁、一鍵返回，附件頁不在線性翻頁順序裡。
